# 2026-08-20

## deferred window geometry

`App.SetWindowSize`/`SetWindowPos` now record the request and flush it from the backend's `afterRender` hook instead of calling glfw where they are invoked. the why is in the comment on the `pending*` fields and in the changelog; what those don't carry:

- **the unit tests prove the contract, not the bug.** `appGeometry_test.go` covers deferral, supersede, and the no-op boundary against a fake backend -- none of which would fail if the deferral were removed *and* the platform were x11. the actual crash only reproduces on a live wayland session, and the cheapest proof is a ~30-line dfx app whose `Draw` calls `state.App.SetWindowSize(...)` on frame 20 and `state.App.Stop()` on frame 50. against v0.1.5 it panics on the imgui assertion; with this change it exits 0. worth rebuilding rather than trusting the test suite if this code is ever touched again.
- **`SetWindowPos` still fails on wayland, by protocol** -- a client may not position its own surface, so the probe prints `Glfw Error 65548` and moves on. that is expected and out of scope here; the consumer has to decide what to do about it (baab treats a `(0,0)` reading from `GetWindowPos` as a non-reading, since glfw zeroes both coordinates on that failure and recording it corrupts saved geometry).
- **`app.go` is not gofmt-clean at HEAD** and was not before this change -- the `Config` struct's comment column disagrees with current gofmt. left alone deliberately: reformatting it would bury a small fix under an unrelated diff. the additions here are gofmt-clean, so `gofmt -l app.go` firing is pre-existing noise, not a regression.

## cross-branch and downstream

`node-canvas` forked before `17f68f4` (the commit that added the geometry API), so it has neither the bug nor this fix; it picks both up whenever it next merges main. and this is blocking baab, which pins `v0.1.5` and cannot consume the fix until a release is tagged -- baab is currently building against this working tree through a gitignored `go.work`.
