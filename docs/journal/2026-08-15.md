# 2026-08-15 — NodeCanvas wheel sensitivity: travel accumulation

Michael's wheel is too sensitive on the NodeCanvas example: the old path stepped one full detent per non-zero wheel frame, so a fast flick walked the whole detent range in a couple of frames.

## Change

`NodeCanvasConfig.WheelStepsPerZoomLevel` (name taken from Michael's suggestion) is the wheel travel — in imgui wheel units, one classic notch being 1.0 — that must accumulate before the wheel produces a detent step. Default 1.0: classic-notch mice keep the one-notch-one-detent behavior, and fine-scroll/trackpad devices (fractional ticks) drop from stepping every frame to stepping per accumulated threshold — so the fix is active at the default for oversampled input. The example sets 2 to demonstrate the knob and to halve the step-per-notch on Michael's mouse; if 2 proves not gentle enough, or a gentler framework default is wanted, it's a one-line change plus a CHANGELOG line.

The accumulator is canvas-side state (`wheelAccum`, beside `leftDragSticky`) driven by the pure helper `advanceWheel` (nodeCanvasInput.go, table-tested in nodeCanvasInput_test.go):

- a direction change resets the banked travel;
- sub-threshold remainder carries across idle frames, so fine-scroll tick streams that straddle frame gaps still accumulate;
- at most one step per frame — a single frame's travel beyond the threshold banks for the next same-direction frame, so the state machine (untouched: it still consumes a sign-only `wheel` and steps one detent) never jumps more than one detent per frame;
- a non-positive threshold reads as 1.0.

Accumulation happens only where the machine could actually step (canvas hovered, no popup open, no in-canvas item hovered, no gesture in flight — the gesture sample is one frame stale, the same accepted staleness as `origin`/`viewport`); otherwise the bank resets, so scrolling over a sidebar or mid-gesture can't bank travel that would later produce a phantom step.

`make test` green. `docs/current/node-canvas.md` interaction line and detents paragraph updated; CHANGELOG CHANGE entry in `## Unreleased`.

## Detents: more steps, and past 100%

Follow-up in the same session: with the accumulator in place, Michael tested slow wheel rotation — it steps fine even at the slowest rotation, so the accumulation model is sound as-is (indefinite, non-draining bank; no decay constant). The real gap he named: not enough zoom steps in the model, and no zoom beyond 100%.

- Default detents extend past the editing detent and gain resolution: final default `{0.25, 0.4, 0.5, 0.6, 0.7, 0.8, 0.9, 1.0, 1.1, 1.2, 1.3, 1.4, 1.5}` — 0.1 steps across the working range, one coarser step from 0.4 to the 0.25 zoom-out floor (the 5px floor he accepted as readable).
- Contract relaxes from "last entry must be 1.0" to "1.0 — the editing detent — must be a member of the set"; entries above are allowed. Full interactive content applies at every detent ≥ 1.0 (the font scales up; widgets behave normally), so apps' `n.Detent() < 1.0` content branches are unchanged.
- Initial view zoom is now the editing detent (1.0) instead of the largest configured one — with the top now at 1.5, opening at the top would have opened the graph zoomed in. (Behavior-identical under the old default, where top == 1.0.)
- `ZoomToFit` still descends from the largest configured detent; because canvas-space content is detent-invariant by construction, the descent is unchanged — small graphs can now resolve above 1.0, which is the desired fill-the-screen behavior.
- Overhead of the finer set (verified against pinned cimgui-go v1.5.0 / imgui 1.92 and the GLFW backend): per-frame cost is flat (detents are just snap targets; rendering depends on the current detent only). Each size the atlas hasn't baked costs a one-time rasterize of the glyphs actually used, and the GLFW backend (classic CPU-atlas path, no `RendererHasTextures`) recreates and fully re-uploads the atlas texture when it outgrows — a few-ms hitch per newly-reached size, texture ceiling a few MB at 13 sizes. `ZoomToFit`'s descent bound grows with the detent count (worst case ~13 frames ≈ 220ms full-range at 60fps). Pinned by new `nodeCanvas_test.go` (constructor defaults: set, sortedness, 1.0 membership, opening zoom, wheel-steps defaulting).
- Docs (`docs/current/node-canvas.md` content-and-detents + detents paragraphs), CHANGELOG entries, and this journal updated. The temporary wheel-delta calibration logging in the example (added to investigate the slow-scroll question) is removed.
