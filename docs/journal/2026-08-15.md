# 2026-08-15 — NodeCanvas wheel sensitivity: travel accumulation

Michael's wheel is too sensitive on the NodeCanvas example: the old path stepped one full detent per non-zero wheel frame, so a fast flick walked the whole detent range in a couple of frames.

## Change

`NodeCanvasConfig.WheelStepsPerZoomLevel` (name taken from Michael's suggestion) is the wheel travel — in imgui wheel units, one classic notch being 1.0 — that must accumulate before the wheel produces a detent step. Default 1.0: classic-notch mice keep the one-notch-one-detent behavior, and fine-scroll/trackpad devices (fractional ticks) drop from stepping every frame to stepping per accumulated threshold — so the fix is active at the default for oversampled input. The example sets 2 to demonstrate the knob and to halve the step-per-notch on Michael's mouse; if 2 proves not gentle enough, or a gentler framework default is wanted, it's a one-line change plus a CHANGELOG line.

The accumulator is canvas-side state (`wheelAccum`, beside `leftDragSticky`) driven by the pure helper `advanceWheel` (nodeCanvasInput.go, table-tested in nodeCanvasInput_test.go):

- a direction change resets the banked travel;
- sub-threshold remainder carries across idle frames, so fine-scroll tick streams that straddle frame gaps still accumulate;
- at most one step per frame — a single frame's travel beyond the threshold banks for the next same-direction frame, so the state machine (untouched: it still consumes a sign-only `wheel` and steps one detent) never jumps more than one detent per frame;
- a non-positive threshold reads as 1.0.

Accumulation happens only where the machine could actually step (canvas hovered, no popup open, no in-canvas item hovered, no gesture in flight — the gesture sample is one frame stale, the same accepted staleness as `origin`/`viewport`); otherwise the bank resets, so scrolling over a sidebar or mid-gesture can't bank travel that would later produce a phantom step.
