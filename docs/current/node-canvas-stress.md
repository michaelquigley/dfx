# NodeCanvas stress harness

Run `go run ./examples/dfx_example_nodecanvas_stress` on a machine with a display. The left control panel has show/hide mini-map and corner-cycle buttons, plus 100, 1,000, 5,000, 10,000, and 20,000-node presets, an adjustable count from 0 through 20,000, a compact grid or separated clusters, spacing, and zero, one, or four outgoing links per node. Mini-map control changes reset and warm the timing samples. The larger presets are diagnostic stress cases; the mini-map's acceptance target remains approximately 5,000 nodes. The fixed seed keeps IDs, positions, order, accents, and links reproducible for the same settings. The panel reports the actual node and link counts. Drag node bodies to move them; middle-drag pans, Ctrl+wheel zooms, F fits, C centers, and 1/2/3 center near the first, middle, or last node. At zooms below 1.0, cards use noninteractive labels while retaining their pins. The example applies selection, raising, movement, and new-link intents to its own model. Changing any fixture control restores the generated scene.

The panel reports a rolling 120-sample median and p95 for two different measurements, after 30 warmup frames. **Canvas CPU** is wall time around `Begin`, declarations, and `End`, including transient hidden fit measurement. **Displayed frame cadence** is elapsed time between consecutive `OnTick` calls; it includes presentation pacing and is neither GPU time nor a direct drawing-cost estimate. Fixture and view-preset changes clear both windows. The backend is GLFW/OpenGL with swap interval 1 (VSync enabled by the cimgui-go backend). Note the exact viewport size and zoom shown in the panel along with count, link count, layout, spacing, OS, and architecture when recording a result.

The opt-in headless benchmarks use the same deterministic generator. `go test . -run '^$' -bench '^BenchmarkNodeCanvasGeometry$' -benchmem` measures bounds and representative node, link, and full-graph miss hit tests at all five presets. `go test . -run '^$' -bench '^BenchmarkNodeCanvasCPUFrame$' -benchmem` submits real ImGui frames without a renderer at those counts. Fixtures and initial layout/channel warmup are outside the timed loop. Neither benchmark measures actual graphics rendering. Run `make test` for the ordinary test and vet gate.

For the interactive baseline, use 5,000 nodes in each layout at link fanouts 0, 1, and 4, at zoom 1.0 and the minimum detent (0.25). For each case, record idle, pan, zoom, node drag, and fit separately. Fit may trigger hidden measurement over several frames; separate its transient peak from steady state after it settles. Repeat on the target machine and note responsiveness and any bottleneck. The stage 1 baseline is the current canvas without a mini-map. Michael's hands-on assessment decides whether it is acceptable before stage 2.

On 2026-10-15, Linux/amd64 on an Intel Core i9-9900K, a short opt-in headless run (`-benchtime=3x`) at 5,000 grid nodes and four links per node measured 14.5 µs for bounds, 4.64 ms for the isolated link hit, and 4.62 ms for an empty-space miss. The CPU-frame benchmark, with one link per node, measured 94.3 ms/frame and 11.7 MB/frame (about 190,000 allocations) at 5,000 nodes. A longer 40-iteration run measured 96.3 ms/frame. Profiling found repeated copying of ImGui's full style-color array when drawing each card's labels and pins; replacing that with a direct color lookup reduced the same 40-iteration benchmark to 35.6 ms/frame, with allocations still about 190,000 per frame. These are CPU submission measurements, not graphics rendering or an interactive frame-rate claim.

The windowed example launched without error under the local GLFW/OpenGL display. Michael's first hands-on pass found 3,000 nodes acceptable and 5,000 nodes choppy before the color-lookup fix. After the fix and addition of 10,000- and 20,000-node detents, he found 5,000 fine, 10,000 mostly fine, and 20,000 a little sluggish. The complete layout/link-density/gesture matrix and its timings remain unrecorded; this hands-on assessment supports the approximately 5,000-node target without establishing a larger-scale guarantee. A 20-iteration headless CPU-frame run at 20,000 nodes with one link per node measured 144 ms/frame, 50.2 MB/frame, and about 760,000 allocations/frame. A 30-iteration geometry run with four links per node measured about 18 ms for a link hit or empty-space miss. These headless figures do not include GPU rendering.
